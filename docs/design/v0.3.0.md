# v0.3.0: CLI blocking waits and default recovery

Release validation: completed on develop on 2026-11-02, including the
user-installed v0.3.0 plugin. The deployment-only main snapshot and v0.3.0
release use the same validated runtime.

## Behavior

- The MCP waiting tool is named `poll`, exposed as `monitor.poll` in CLI. It
  replaces the previous `monitor_wait` name; this does not add model polling.
- The public API has eight tools without the redundant `monitor_` prefix:
  `start`, `stop`, `event`, `status`, `validate`, `display`, `poll` and `recovery`.
  `status` combines summaries, active lists, full evidence and UI revision waits;
  it never starts a service or recovery. `event` combines inspection and
  acknowledgement via optional `resolution`. `stop(target: "wait")` releases
  waiting and mutes selected notifications, preserving observers, processes and
  the native goal; `stop(monitor_id: ...)` stops an observer. Exactly one target
  is required. The separate public `report`, `ack` and `cancel_wait` operations
  are removed. Native callback output also uses namespace `monitor`, name
  `event`; internal envelope types, event reasons and sensor event names remain
  unchanged. This is a v0.3.0 tool-name migration; old aliases are not registered.
- `poll` defaults to `mode: blocking`. It holds the current MCP request
  open and leaves the native goal active. No repeated model request is made
  during a quiet wait. Monitor events return in that same call.
- Omitting `timeout_ms` uses a one-hour blocking wait (`3600000`), filled by both
  the MCP schema and local service. A valid supplied timeout takes precedence;
  callers need not include the argument for the default. Maximum is 24 hours.
- CLI input-history sampling defaults to 250 ms and can be 50–5,000 ms. It runs
  locally, not as agent turns. An exact-thread new input record releases the tool
  so Codex can consume its queued input itself. No message is replayed.
- `mode: pause` retains the existing authorized native goal pause/callback flow.
  Manual resume of the same live paused goal releases the old wait without
  muting observers or suppressing pending evidence. Goal edits, manual pauses,
  explicit cancellation, budget exhaustion and interruption still win.
- First monitor/wait use in a new thread enables recovery once: `all_failed`,
  fixed 300-second delay, 3-hour incident limit, separate 24-hour supervisor
  lifetime. Setup defaults to on and offers `recovery: false`. A per-thread
  disable, manual interruption, exhausted policy, ambiguous delivery or service
  restart is never overridden by another monitor operation.
- Event structured results include observation-time `timing.wait_elapsed_ms`
  with an explicit poll/monitor basis, plus `timing.monitor_elapsed_ms`.
  Blocking results also include total `elapsed_ms`. Agents use this data for
  planning; regular callback text, result cards, hooks and HTML views do not
  add elapsed-duration output.

## Why input history

Native experiments use Codex CLI 0.166.0, a disposable `CODEX_HOME`, a synthetic
local Responses SSE provider and no credentials/paid model calls.

An ordinary MCP tool may remain pending while the goal stays active. However,
`turn/steer` accepts additional input without immediately emitting a user-message
item. `thread/read(includeTurns: true)` and full `thread/turns/list` snapshots
were identical before and after steering while the tool remained blocked. The
user-message notification and `UserPromptSubmit` processing happen when pending
input is drained after the in-flight tool. Polling these history APIs cannot
solve this case on the tested host.

The CLI also appends submitted prompts to `history.jsonl`, with `session_id`,
`ts` and `text`. A real Linux CLI pseudo-terminal experiment confirmed the
append occurs while an MCP call is blocked. A matching new record released the
call, and the next model request contained both its result and the actual user
message. The adapter is version-specific, not a public cross-client input-queue
contract. Desktop support is not established.

The reader snapshots the initial byte offset and tails bounded chunks only.
It handles split UTF-8 and partial lines, rejects old/other-thread messages, and
does not expose prompt text. File replacement, truncation, unavailable reads or
oversized records release rather than trapping a call indefinitely. Missing
input history refuses blocking; native `config/read` also rejects an explicit
`history.persistence = "none"` even if an old history file remains. Input history
must be enabled in the CLI; per-process overrides outside the daemon's effective
configuration cannot be proven by this check.

## Ownership and delivery

Only one wait owns the thread. Registration checks unresolved events, live
observers, finite deadlines, sensor errors and expiry fallbacks. Thread scope
includes later registrations. Training still needs workload health detection;
the wait timeout is not a training watchdog.

While blocked, callback injection is held. A matching event transitions from
`pending` to `returned`; it remains unhandled until explicitly acknowledged.
That transition records a prepared tool result, not guaranteed host receipt.
Restart makes unsettled returned delivery unknown; it must be reconciled before
replay. History cleanup and installation guards preserve this evidence.

`stop(target: "wait")` also invalidates an in-flight preparation check, so a
late host response cannot attach a new blocked wait after cancellation. Cancelling
an attached wait returns `cancelled` in both the pending result and saved state,
and mutes only the selected notifications without ending observers or the goal.

MCP cancellation and local HTTP cancellation propagate to the pending wait.
Transport loss releases resources, preserves observers, and holds callbacks.
Reconnection requires evidence reconciliation and a new attached wait. Actual
service restart still marks observers unknown and never reruns an owned command.
Manual interruption suppresses the affected notifications and cancels recovery.

The MCP tool timeout is 86,420 seconds; the wait maximum is 86,400 seconds and
the local RPC has a cleanup margin. User/host overrides can shorten the limit.
Local RPC uses Node HTTP with the caller's finite deadline, rather than fetch:
the bundled Undici client otherwise imposes an independent 300-second response
headers timeout and can prematurely end a one-hour blocking poll. Caller aborts
close both quiet-header and partial-body responses.
Goal wall-clock accounting may continue while the goal is active. No claim is
made that blocking saves elapsed-time budget or bypasses host limits.

Wait requests capture cancellation before default recovery initialization. They
prepare input observation concurrently with initialization, so a stop during a
slow host check cannot be lost and followed by late wait attachment. Pause-mode
responses refresh the same wait's state after initialization rather than
returning an earlier waiting snapshot after cancellation.

Recovery configuration handles manual interruption, goal pause/clear and thread
closure while it is still configuring. Explicit opt-out does not wait for
default initialization to finish; stale responses and late host errors cannot
overwrite that newer choice. Full thread status also preserves omitted-event
counts when its evidence list is bounded to eight records.

## Evidence and remaining limits

- A live demo in the current conversation used the development MCP service with
  isolated monitor state and the actual native goal. A real additional user
  message released the pending call with `user_input`; a subsequent safe file
  write released another call with `monitor_event`. Both reads confirmed the
  goal remained active. The demo then acknowledged its event, stopped recovery,
  shut down its isolated services and completed its goal. The installed v0.2.4
  plugin was not replaced; its existing tool list cannot show the new `poll`
  function until the new bundle is loaded.
- Windows native App Server/MCP: event, input signal, timeout and cancellation release the
  original turn while the goal remains active; no extra turn during quiet wait.
- Windows input-tail tests: exact-thread matching, old/partial/Unicode records,
  replacement, timeout, disconnect, reattachment and default recovery policy.
- Real Linux CLI pseudo-terminal: actual submitted input writes the early hint
  and arrives in the model's next request with the tool result.
- Existing pause compatibility, manual stop and recovery limits remain covered
  by the runtime/native/network suites. Reduced API coverage verifies read-only
  empty/saved/live status, full evidence, explicit stop targets, owned-command
  preservation, event inspection/resolution and idempotent settled events.

Validation on 2026-11-02:

- Windows final full suite: 249 tests, 242 passed, 7 platform-dependent skips, no
  failures or cancellations (Node 24.22.0, Codex CLI 0.166.0).
- Ubuntu 24.04 isolated Docker final full suite: 249 tests, 244 passed, 5 skips, no
  failures or cancellations (Node 24.22.2, Codex CLI 0.166.0), including the
  real CLI pseudo-terminal input-wake test; test execution had networking off.
- Both final suites include the short MCP tool names, native `monitor.event`
  callback routing, the optional one-hour timeout default and structured-only
  event timing, selected-wait cancellation and cancellation during host
  verification, manual interruption/opt-out during recovery initialization,
  cancellation during service initialization, bounded full-evidence counts,
  local HTTP deadline/caller cancellation and split UTF-8 responses.
  Native plugin discovery and isolated installation/replacement
  probes passed. A separate packaged MCP check enforced exactly eight public
  IDs and executed `status`, preserving the stable `monitor_report` envelope.
- Build, deployment packaging and skill validation passed. The package includes
  the new input-history runtime and excludes source, tests, workflows and local
  state. A subsequent publication review repeated both full suites through the
  user-installed v0.3.0 plugin with the same totals and zero failures. Its runtime
  hashes match the built candidate; the review did not replace the installation.
- Publication checks installed locked production dependencies into an isolated
  deployment package and verified its eight-tool MCP discovery, execution and UI
  resource. The legacy Windows compatibility suite passed 115 tests with 18
  platform skips. The local skill-link validator now handles URL fragments in
  relative links; existing targets pass and missing targets still fail.
- The README's three mechanism flowcharts passed Mermaid parsing. They describe
  event delivery, input-aware CLI blocking and bounded recovery.
- A separate Windows quiet-header test held the local response for 310 seconds.
  The original fetch transport failed after 307.451 seconds with
  `HeadersTimeoutError`; the current HTTP RPC returned successfully after
  310.047 seconds. Both used the same isolated endpoint concurrently and a
  335-second caller deadline. This establishes removal of the observed
  five-minute transport ceiling; it is not a full one-hour soak test.

The first Windows full run passed its behavior assertions but hit an ENOTEMPTY
fixture cleanup race while the local service finished shutdown. Bounded cleanup
retries resolved it; the final full run above passed. The first Ubuntu attempt
failed before building because Docker context metadata was temporarily locked;
subsequent builds and final isolated tests passed. Neither failed attempt is
counted as successful validation.

Native tests also caught delayed initial goal notifications during attachment.
Preparation now takes its goal-action baseline after the authoritative goal
read, permits ordinary usage accounting, and rejects subsequent manual changes.
The fixture exits with an explicit refusal rather than hanging if attachment is
rejected. Failed turns preserve observers and queued evidence for recovery;
manual interruption and explicit task changes still suppress obsolete callbacks.

The Windows automation host cannot allocate an interactive pseudo-terminal for
the CLI in this session. Windows native MCP/input-tail coverage does not by
itself constitute an end-to-end Windows interactive keyboard test.
