# v0.2.4 design: monitor capacity and concise CLI interaction

Status: draft requirements and proposed interfaces. Capacity, short-invocation
and active-detail interfaces below remain proposed. The duplicate-report prompt
cleanup described below has been applied on develop. No version bump,
installation change or release publication has been made. Additional v0.2.4
requirements can be added here.

## Requested experience

1. Warn before a thread exhausts its 32 active observer slots. Guide the agent to
   reconcile obsolete observers and consolidate monitors with compatible purposes.
   A capacity rejection must explain what to do next.
2. Keep the Stop/Interrupt report short, with access to the active monitor list.
   Do not list stopped, cancelled or otherwise inactive history in routine output.
3. Keep monitor invocations short. The screenshot of `monitor_wait` shows that
   long input JSON, especially `resume_instructions`, dominates the conversation
   even when the result is already a single line. Full details should remain
   accessible without repeating them in every invocation.
4. Let trusted Stop/Interrupt hooks provide routine end-of-turn status. Remove
   skill/default-prompt/tool instructions requiring the agent to check and report
   monitors just because a turn is ending. Keep operational checks, obsolete
   monitor cleanup, event handling and confirmed goal-pause requirements.

## Remove duplicate end-of-turn reporting

Applied to skill instructions, the invocation default prompt, MCP server/tool
instructions, event callback guidance and current user documentation:

- Neither compact nor verbose mode requires an end-of-turn `monitor_report` call
  or an additional status sentence in the assistant's final answer.
- Trusted Stop/Interrupt hooks retain their automatic, bounded, read-only report.
- Explicit reports remain available on user request and when needed to operate,
  clean up or diagnose monitors. An untrusted, disabled or unavailable hook does
  not silently reinstate a per-turn model reporting requirement.
- Registration readiness, unresolved-event checks, wait guards and verified
  native goal pause remain operational requirements. Removing a redundant report
  does not remove the pause barrier or authorize skipping event reconciliation.
- Required observers and authorized recovery may continue across turns; obsolete
  observers and handled events are still reconciled promptly.

## Host findings

Inspected installed Codex CLI 0.166.0 and upstream source at `rust-v0.166.0`.
These are version-specific findings, not claims about every Codex client.

- Ordinary MCP invocation headers serialize the original argument JSON. Tool
  titles, output text and the plugin's `compact` preference do not replace it.
- Normal MCP result text has a bounded preview; the Ctrl+T transcript retains the
  full result text. `structuredContent` alone is not a human-readable CLI detail
  view, and changing result text cannot shorten the invocation above it.
- Stop/Interrupt `systemMessage` output is rendered as hook text. It has no
  separate collapsed-summary/expanded-body fields in the inspected host path.
- MCP tool hooks are available, but their text output is processed through the
  hook output contract. Changing a command hook to an MCP hook does not by itself
  create an ordinary expandable MCP invocation card.
- MCP Apps can provide an interactive panel in supporting graphical clients;
  this does not supply that panel in the CLI.

References:

- [Official Hooks documentation](https://learn.chatgpt.com/docs/hooks)
- `codex-rs/tui/src/history_cell/mcp.rs`: invocation serialization, result preview
  and transcript rendering.
- `codex-rs/tui/src/history_cell/hook_cell.rs`: `systemMessage` rendering.
- `codex-rs/core/src/hook_mcp_executor.rs`: MCP hook text extraction.

Literal click-to-expand hook output and arbitrary replacement of input JSON
cannot be promised by a plugin alone on this CLI. Do not spoof a privileged
server name, inject terminal controls or patch the user's Codex executable to
obtain another renderer.

## Capacity feedback

Keep the hard limit at 32. Proposed early warning: 24 occupied slots, leaving
eight slots to introduce replacements before retiring compatible observers.
Use `>= 24` and `>= 32`, including the registration that crosses the threshold.
The threshold is a proposed default, not an existing configuration option.

Count actual reserved observer slots in `Manager.jobs`. Starting and stopping
observers occupy slots until their sensor releases them. Muting notifications
does not free a slot. Historical records and recovery supervisors do not occupy
observer slots. Equivalent live registrations remain reusable at the limit.

Expose machine-readable capacity in live operation reports and status:

```json
{
  "capacity": {
    "used": 24,
    "limit": 32,
    "warning_at": 24,
    "remaining": 8,
    "state": "warning"
  }
}
```

States: `normal`, `warning`, `full`. Unavailable/saved state must not claim a
verified live capacity. Reports filtered to one monitor must still report the
thread's actual capacity, rather than the filtered record count.

At warning pressure, add one concise line to the next real operation/report:

```text
Monitor · 24/32 slots in use · review obsolete and overlapping monitors
```

At the hard limit, return a specific `MONITOR_CAPACITY_EXCEEDED` error, current
capacity and a next-action hint. Preserve this code through the service/RPC/MCP
layers instead of replacing it with `MONITOR_REQUEST_FAILED`.

```text
Monitor · limit reached (32/32). Reuse an existing monitor, reconcile obsolete
observers, or inspect compatible consolidation candidates before trying again.
```

Warnings do not emit callbacks, wake the model, open extra turns or repeatedly
schedule reports. Detailed candidates belong in explicit status/structured
results. The agent should act on an existing capacity warning instead of blindly
retrying registration or repeatedly retrieving the same report.

### Consolidation guidance

First reconcile already handled events and truly obsolete live observers. A
stopped historical entry needs no stop call and deleting it does not free a slot.

Then inspect candidates using their actual source, workload identity, trigger
rules, notification policy and registered next action. Similar names or a shared
working directory alone are insufficient evidence of equivalence.

Potential reductions include:

- Reuse an equivalent live registration instead of starting a duplicate.
- Combine one workload's compatible PID, progress and GPU health conditions in
  one watchdog when its AND/OR semantics remain correct.
- Combine equivalent completion-artifact observations with a narrow directory
  pattern when every relevant artifact still has an identifiable event and the
  same handling policy.

Preserve per-workload stall detection. A healthy file in a shared directory can
hide another workload's inactivity; that is not a valid replacement for independent
training watchdogs. Preserve deadlines, error/expiry delivery, event evidence,
pending events and an existing goal wait's guards and wake scope.

Verify replacement coverage before retiring a live observer. Never stop an owned
command to free capacity unless terminating that workload is already authorized.
Consolidation may be impossible when all observers represent independent work.
At full capacity, report that constraint rather than disabling required coverage
or claiming that deleting history solved it. An automatic or transactional merge
API is not assumed by this design.

## Short monitor invocations

Proposed backward-compatible change to `monitor_wait`:

- Make `resume_instructions` optional.
- When refreshing a verified active wait, omission reuses that wait's saved
  instructions. Supplying a value explicitly updates them as today.
- For a new wait, omission uses a small built-in action: inspect the triggering
  event and its registered instructions, reconcile effects, and continue the
  existing task within the user's authorization.
- Do not inherit stale instructions from an ended wait or an unrelated thread.
  A service restart must not silently revive an interrupted wait or its authority.
- Keep explicit authorization and existing goal pause ownership/barrier checks.
  Omitted instructions do not grant permission to pause or resume a goal.

The ordinary call can then be:

```text
monitor_wait(thread_id="…")
```

Thread scope is already the default. Include selected IDs, scope overrides and
goal authorization only when required by the actual operation. Authorization
must still be supplied when current verified ownership does not retain it.

Update skill/tool guidance to keep instructions focused on the event's next
action. Store lengthy progress notes in the task's existing handoff document and
refer to its path when useful; do not copy the whole task history into monitor
arguments. Referenced file contents remain untrusted data and do not add authority.
Do not compress operational instructions into opaque encodings.

For long start commands/configuration, consider a later, separately specified
validated configuration reference. It must not be simulated by dropping required
parameters or by moving the same huge JSON into another routine tool call.

## Active detail view and stopping reports

Preserve the automatic hook's compact default:

```text
Monitor · 3 running
```

The proposed explicit detail request is:

```text
monitor_report(thread_id="…", details="active")
```

It should produce human-readable text as well as structured fields:

```text
Monitor · 3 running
  training-A · running · watchdog
  training-B · running · watchdog
  evaluation · running · command
```

List only active observers, with stable IDs in the full detail view so same-name
entries can be distinguished and inspected. Include starting/stopping states
honestly; never label an unverified historical observer as running. Keep commands,
authorization, raw evidence and inactive history out of this list. Bound and
sanitize all labels, and retain a total/omitted count if any view is truncated.

The current CLI can preview and expose this tool result through its native
transcript controls. This is a fallback detail path, not a clickable Stop hook.
The default report remains one line. An explicit active-detail request can show
several preview lines; the plugin must not promise that the host collapses it to
exactly one. `verbose` may use the same active-only detail renderer by default.

If a future supported host exposes separate hook summary/detail fields, use
those fields to attach the same sanitized active list. Until then, keep the hook
short and do not create a model continuation or block Stop merely to manufacture
a tool call. Graphical clients may use the existing MCP Apps panel separately.

## Acceptance checks before implementation is released

- Threshold boundaries: 23 -> 24, 31 -> 32, rejected 33rd registration and
  equivalent-registration reuse when all slots are occupied.
- Concurrent registrations never exceed 32; stopping releases capacity only
  after sensor cleanup, and muted live observers still count.
- Settled history does not count; per-monitor status does not undercount the
  thread; stale snapshots never claim verified capacity.
- Capacity error codes and actionable hints survive a real MCP/service round
  trip. Pressure feedback causes no callback/model request.
- Consolidation guidance preserves independent stall detection and never
  suggests killing owned commands just to tidy the list.
- Omitted wait instructions work for new waits and verified in-place refreshes;
  explicit updates still work. Ended/restarted/foreign waits do not leak context
  or authority. Existing manual-pause and early-event barrier tests still pass.
- Active details omit inactive history, sanitize labels, distinguish duplicate
  names and refuse to present saved states as verified running.
- Stop/Interrupt stay bounded and read-only, with no block/continue decision,
  daemon startup, synthetic MCP call or extra model turn.
- Inspect actual CLI presentation, including argument length and transcript
  details. JSON assertions alone do not establish a clickable or graphical UI.
- Test runtime changes on Windows and Ubuntu before release. Record native UI
  limitations separately from runtime test results.
