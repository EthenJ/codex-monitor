# Node GPU 验证

在 `develop` 构建后运行，测试使用本机 `nvidia-smi`，不需要模型 API key。GPU 利用率是整张设备的指标：同卡上的其他任务可能掩盖某个训练任务的停滞，因此训练监控应同时观察实际进度文件和 PID。

## 1. 不影响训练的实机检查

```bash
npm run build
CODEX_MONITOR_TEST_GPU=1 node --test --test-timeout=25000 tests/node/gpu.test.mjs
```

检查索引、完整 UUID、PCI 地址、多卡选择、无效 UUID、连续采样和有限期限退出。阈值为 0%，任何有效利用率都不应产生低利用率报警。只读取指标，不分配显存或终止训练。可用 `CODEX_MONITOR_NVIDIA_SMI` 指定可执行文件。

## 2. 在实际利用率变化中观察触发与恢复

```bash
node tools/probe-gpu-transitions.mjs \
  --gpu-id all --gpu-match any \
  --below 100 --recover 100 --dwell-ms 250 \
  --sample-ms 200 --timeout-ms 60000 > gpu-transition.jsonl
```

这是诊断参数，不是生产报警配置：同一张卡低于 100% 持续至少 250 ms 即满足低利用率条件；`any` 模式恢复要求所选卡均达到恢复阈值。利用训练原有波动验证真实采样到事件的完整链路，不修改训练。JSONL 中保存原始采样值、事件、单调时钟时间和最终结果。

- 退出码 `0`：实际观测到触发及恢复。
- 退出码 `1`：传感器/参数等错误，需要查看日志。
- 退出码 `2`：期限内没有完整转换，或人工取消，结果不确定；不能记为通过。

默认参数是低于 10%、恢复到 20%、持续 1 秒、最多观察 60 秒；可选 `--gpu-id 0` 或 `--gpu-match all`。探针限制为最多 120 秒、采样间隔至少 50 ms。生产监控应根据真实训练的正常加载/验证间隔选择更长的 dwell 和 grace。

2026-11-01 Ubuntu 实测：两块 RTX 4090 D、驱动 610.57.04。首次探针读取 10 次样本，在 98%/83% 持续约 292 ms 时触发，之后两卡回到 100% 时恢复。提交到仓库的可复用探针再次通过，读取 27 次样本，约 7.76 秒完成；触发样本为 100%/99%，随后为 100%/100%。两次测试结束都通过原生工具结果通知当前会话，结果已检查并 acknowledgement。没有向现有训练进程发送信号。

这证明真实驱动采样、dwell、事件触发和恢复链路工作；它不证明训练真正停滞、实际利用率下降到 0–10%，或真实驱动失效后恢复。

随后还通过插件本地服务直接注册了 GPU watchdog（相同诊断阈值、最多两个事件、45 秒期限）。真实采样在 100%/99% 持续约 306 ms 时触发，随后恢复；`watchdog_stalled` 和 `watchdog_recovered` 均作为原生工具结果到达原会话，已检查并确认处理，观察器到达事件上限后自动停止。这一轮覆盖 GPU 事件本身的投递，而不只是探针进程结束通知。

## 3. 可重复的传感器故障与恢复测试

```bash
node --test --test-timeout=25000 tests/node/gpu-provider.test.mjs
```

POSIX 测试启动一个隔离的可执行采样程序，走与 `nvidia-smi` 相同的子进程、CSV 解析、健康判定和取消路径：

- 持续低利用率只报警一次；15% 落在 10%/20% 滞回区间，不误报恢复。
- `N/A` 标为 unknown 且连续故障只报一次；恢复读到低值不重复报警，读到高值才恢复，之后能再次触发。
- 非 CSV、重复设备、缺失选定设备、驱动命令非零退出都属于传感器错误，不被当成 0%。
- 查询一直卡住时，主动取消和监控到期都会清理查询进程，不等待完整的 10 秒采样超时。

三个测试已在 Ubuntu 的 Node 22.22.0 和 24.17.0 通过。它们不需要 GPU，适合在 Docker/CI 中重复执行；当前可执行 fixture 使用 POSIX shebang，Windows 明确跳过，不据此推断 Windows 驱动进程行为通过。

本机 Docker 29.1.3 中也已通过这三个测试：Ubuntu 24.04、Node 24.22.2、UID 1000、关闭外网且未接入 GPU。完整容器套件为 69 项，66 通过、3 项预期跳过。

## 4. 何时才需要暂停任务

上述检查均不需要停止训练。本机两张 GPU 都被训练和其他计算进程共享，暂时不执行人为降载。

若需要进一步证明实际利用率从低于 10% 上升到至少 20%，优先选择空闲 GPU 和独立的短时负载。若没有空闲卡，则需要先安排 checkpoint，并取得暂停共享该卡的所有相关任务的明确授权。跨卡训练应按训练程序支持的整体暂停/恢复方式处理，不能单独冻结某个分布式 rank。具体进程、保存位置、恢复命令和允许暂停时间须在操作前列明。
