# codex-monitor v0.2.2

This release makes setup interactive, validates MCP configuration before starting work, and reduces routine CLI output. The eleven MCP tools preserve native event delivery, goal waiting and the bounded recovery policy from v0.2.1.

## Interactive installation

Run `node install.mjs` from the complete source checkout or deployment package. The wizard asks for the Codex configuration directory, client, display mode, Stop/Interrupt reports and launcher startup, then shows a plan for confirmation. Existing installations require an explicit replacement choice. `--dry-run` previews the plan; `--config FILE --yes` supports reviewed agent-assisted answers.

Setup builds source when needed, prepares a separate deployment bundle, installs locked production dependencies, and verifies all eleven tools through a fresh isolated MCP connection. It actually executes `monitor_display` and `monitor_report` before registration and from the installed cache afterward. A shared packaging allowlist excludes tests, workflows, TypeScript, development dependencies and local state.

Upgrades use supported Codex plugin commands and preserve unrelated settings and monitor state. Active monitors, waits, recovery and unresolved pending/unknown deliveries block replacement. The installer never cancels workloads automatically. Idle old services and the launcher are stopped before replacement; the old deployment source remains available for diagnosis. Registration is not transactional: a partial failure reports retained paths and requires inspection before retry.

Setup prints the activation steps: fully reopen Codex, confirm `/plugins` and `/mcp`, actually execute the new tool, review the exact reporting hooks in `/hooks`, and run the external launcher again after login/reboot. Installation does not grant hook trust or enable automatic recovery. A simulation can use a separate Codex home without copying account credentials. See the [installation guide](../../codex-monitor/references/installation.md).

## Configuration and validation

- MCP schemas expose types, ranges, enums and field descriptions. Unknown fields and invalid source combinations are rejected. `kind` is inferred, commands without `match` observe exit, and finite defaults reduce required configuration.
- `monitor_validate` previews normalized settings, checks and warnings without starting workloads, observers, recovery or a model turn. Checks include filesystem access, state-directory aliases, PIDs, optional NVIDIA queries and the exact loaded host thread.
- Start repeats local prerequisite checks because a preflight snapshot can become stale. Invalid starts create no observer or event; invalid recovery updates preserve an existing policy.
- Fix a concurrent service-start race when another caller releases the startup lock between owner lookup and metadata inspection.
- Forward the configured Codex/monitor directories into the MCP process explicitly, so custom state roots and installation display defaults work through real Codex plugin loading.
- Fix Windows MCP startup by using plugin-relative `cwd: "."` and script paths rather than unsupported `${PLUGIN_ROOT}` expansion in MCP cwd.

## Compact events and reporting

`monitor_event` shows the selected trigger, exit status and whether it needs review, with full evidence and registered actions in structured data. After handling, a resolution acknowledges those events and returns the current report in the same result. Already settled events stay settled; naturally completed monitors need no redundant stop call.

`monitor_display` selects compact or verbose presentation per thread without restarting. The installer can set the default for new threads; explicit thread preferences take precedence. Preferences live outside the plugin bundle, so changing them does not invalidate hook trust.

Compact mode reuses fresh reports returned by operations and avoids redundant status/ack/stop/report calls. Verbose keeps diagnostic detail. Native callbacks are readable text with exact event references, not a JSON dump. Raw workload evidence remains in structured results. Codex still owns tool-call headers; the plugin cannot hide calls that actually occur.

`monitor_report` and trusted Stop/Interrupt hooks show a single human-readable line such as `Monitor · 2 running`. Inactive monitor lists and lifecycle history are omitted. Unverified saved state is reported as unavailable. Hooks do not block a stop, enable recovery or create a continuation. The skill directs the agent to clean up obsolete observers and handled events while preserving monitoring still needed for pending work.

## Optional graphical panel and CLI limits

All eleven tools retain an MCP Apps resource and inline display metadata for compatible graphical hosts. The panel shows active workloads, selected triggers, recovery and bounded lifecycle history. Its bounded event waits do not invoke the model; hidden/disconnected views stop automatic refresh.

Codex CLI 0.166.0 displays plain-text tool results and does not render the HTML panel. The background native callback wakes the agent; it does not create an independent visible arrival card. The awakened agent calls `monitor_event` to display the trigger. Desktop HTML rendering remains unverified. Correct resources and metadata are not proof of graphical rendering.

Stop runs when the turn actually ends. A queued callback can keep a turn active; manual interruption uses Interrupt. Finish all installation work before hook review: Codex fingerprints the complete bundle, and subsequent edits can invalidate trust. Existing MCP connections or cached hook catalogs may require reopening the session.

## Validation

Windows, Node 24.22.0, Codex 0.166.0: **132 tests, 126 passed, six expected platform/hardware skips, zero failures**. TypeScript compilation, skill validation and deployment packaging checks passed. New installer coverage includes real Codex registration and replacement in an isolated path containing spaces and Unicode, both hook choices, fresh tool execution, launcher replacement, preference precedence, dry-run behavior and failure boundaries. Tests use temporary Codex homes and synthetic local providers; they do not change the user's installed plugin or use paid models.

After the user reinstalled this version, the installed runtime, MCP configuration, installer and skill matched the development checkout. The actual conversation executed `monitor_display` successfully. A fresh App Server scan found both reporting hooks enabled and trusted; normal completion and manual interruption each executed the installed hook and returned `Monitor · none running`, with exactly two synthetic requests and no reporting continuation. The user's configuration and installed bundle were not modified by verification.

The earlier [18-job CI baseline](https://github.com/EthenJ/codex-monitor/actions/runs/41272897850) covered Node 22/24 on Windows, macOS and Ubuntu, containers and legacy helpers at commit `948c957`. It predates the final CLI and installer changes and does not establish their cross-platform acceptance. New installer acceptance on Ubuntu/macOS and desktop visual acceptance remain pending.

## Unchanged boundaries

- Recovery remains opt-in: fixed 300-second intervals and a three-hour incident window by default, both configurable. Manual interruption, explicit goal/host stops and ambiguous submissions remain protected.
- Goal waiting uses the native goal and requires actual pause/resume authorization. Installation creates no goal and grants no recovery authorization.
- Submission, turn completion and acknowledgement are distinct; exactly-once execution and immediate tool preemption are not promised.
- Stat-based file polling can miss writes with unchanged metadata or transient changes between samples. Native notifications and polling are not an audit log of every write.
- Watchdogs never kill observed training PIDs. Owned command monitors retain process-tree cleanup on cancellation and deadline.
- `main` and release archives contain deployment files only; development source, tests and workflows remain on `develop`.
