# codex-monitor v0.2.2

This release candidate adds typed configuration, preflight validation, native result cards, an optional live status panel and end-of-turn reporting. Main and published tags remain unchanged during validation.

## Changes

- Expose explicit command/watchdog and recovery schemas through MCP `tools/list`: types, ranges, enums, descriptions and rejection of unknown fields. The existing request shape remains compatible. Infer `kind`; commands without `match` observe exit only. Finite defaults reduce required configuration.
- Add `monitor_validate` with structured `valid`, normalized settings, checks, errors and warnings. Validate source combinations, regex/encoding, filesystem access, state-directory aliases, existing PIDs, optional NVIDIA queries and exact loaded-host/goal availability. No workload command, observer, recovery or model turn is started by preflight.
- Repeat configuration and local prerequisite checks automatically on start. Invalid starts create no observer or event; invalid recovery configuration preserves an existing policy. Schema errors use MCP errors; local semantic/environment failures include structured validation details.
- Add `monitor_report`, a read-only MCP tool returning compact structured monitor, event, wait and recovery status. It never creates a service. Saved state is explicitly unverified; history is bounded and raw evidence, commands and authorization are omitted.
- Add `Stop` and `Interrupt` hooks that emit the same report as a structured host status message, with no continuation or callback submission. The user must review/trust the exact hook definitions in Codex `/hooks`. Installing a plugin alone does not trust them.
- Fix a concurrent service-start race: if another caller releases the startup lock between owner lookup and metadata inspection, retry acquisition instead of failing with `ENOENT`. A deterministic regression fails against the previous implementation and passes with the fix.
- Add readable summaries and an MCP Apps resource to all nine tools. The live panel displays counts, recovery policy and a bounded 128-transition timeline; no workload HTML, external assets or model refresh messages are used.
- Track monitor, event-delivery, wait and recovery transitions with a persisted revision. UI requests wait for a change for up to 25 seconds, with cancellation cleanup and a 32-viewer cap. Healthy sensor samples stay out of the journal. Missing/legacy services degrade to explicitly labelled snapshots without starting a service.
- Document authorized hook setup: when the user has requested it, the agent can review and trust this plugin's exact Stop/Interrupt hooks through `/hooks`, without requesting the same approval again. No global trust bypass or self-granted trust is added.
- Fix actual Codex MCP startup by using plugin-relative `cwd: "."` and script arguments. Codex 0.166.0 treated the previous `${PLUGIN_ROOT}` MCP cwd literally on Windows and failed with OS error 267. Hook command expansion remains separate and unchanged.

The plugin now exposes **nine MCP tools**. Fixed 300-second recovery and the three-hour incident window remain unchanged. No public tag or main merge is performed while this candidate is tested.

## Reporting behavior

Agents call `monitor_report` before yielding to produce a real MCP tool result. Trusted hooks also generate a report automatically when stopping or interrupted, using the exact hook session ID. They do not block a stop, enable recovery or start a new model request. Hosts control rendering: hook output is a `systemMessage` through the hook event stream, not a fabricated MCP invocation. Codex 0.166.0 `exec --json` can omit that message even though the hook executes.

A passed preflight is a snapshot, not a guarantee of later readiness or delivery. Custom NVIDIA executables supplied in configuration are executed for a bounded metrics query. Workload commands are never run by validation, so their availability and success remain unverified. Observer startup and callback delivery retain their own lifecycle checks.

## File polling boundary

Extended Windows CI captured a missed immediate nested-file creation with exactly identical directory metadata before and after the write (`mtimeMs: 1793506887465.942`). Stat-based polling cannot detect such a change. It can also miss same-size writes with unchanged modification time and transient changes between samples. This limitation is now documented and included in preflight warnings; the runtime does not promise to record every write or add expensive tree scans.

The readiness regression seeds older initial metadata so its immediate post-readiness writes are distinguishable without sleeping. It repeats the full create/rewrite/replace/delete/recreate cycle 50 times for polling, retains failure-time metadata and keeps the three-second per-event deadline. The separate 60-second test budget allows the repeated cycles to finish in containers. Prior diagnostic runs included 2,400 local immediate create/rewrite iterations and 200-cycle cross-platform stress runs. Those larger runs helped identify the boundary; they do not remove polling's metadata limitation.
